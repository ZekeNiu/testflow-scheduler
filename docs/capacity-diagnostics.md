# 容量瓶颈预警

## 界面与判断

全局容量建议链接到“站点运行与排队情况”的内嵌预警。站点名称旁的标签可查看判断依据；预警可定位时间轴或进入对应容量试算行。试算不自动改动方案，应用后仍可撤回。

所有启用且容量小于本次人数的站点分别增加 1 人容量，完整重算总时长、人均累计等待及全场峰值等待。复用原有排程引擎，支持独立工位、整批测试、三种排程模式、到场安排和休息。

- 可缩短总时长：该次试算缩短总时长；同等最高提速收益的站点均保留优先提示。
- 可减少等待时间 / 可降低等待人数峰值：总时长不变，对应等待指标改善；其他指标变差时明确提示取舍。
- 需关注等待情况：人均本站等待最高但试算未确认改善，不等于本站容量不足。

自动分批到场会随容量重算；各站单独试算收益不可相加。单站 +1 无收益不代表不存在共同瓶颈。整批测试增加的是每批人数上限，不是新增并行设备。数字按既有毫秒精度计算，基于固定耗时和准时执行，不是现场实时监测。

## 维护

`src/testflow-diagnostics.js` 是独立、可测试的诊断模块。`src/testflow-capacity-ui.js` 由 `build.py` 在 UI 首次渲染前装入同一闭包，沿用现有持久化扩展方式；构建会校验唯一初始化锚点，避免上游结构改变后静默失效。原始排程、数据格式、持久化与导出逻辑未改动。缓存仅保存一个配置的紧凑试算指标，不保存多份人员排程。

运行 `npm test` 和 `python3 build.py`。可选 UI 测试：安装 Playwright 与 Chromium 后运行 `python3 tests/capacity-browser.py`；可通过 `TESTFLOW_CHROMIUM` 指定浏览器。该测试离线渲染完整页面，使用内存存储 fixture，不替代真实磁盘持久化测试。

## 文案、样式与关闭状态（2026-10-01 修订）

容量说明按站点类型明确写为“可同时测试人数”或“每批人数上限”，不使用“容量 1 → 2 人”或“单站 +1”等简写。诊断正文说明当前人均等待、最长等待和峰值等待人数，以及具体调整方式、预计改善和可能增加的等待指标。总时长改善同时给出调整前后数值。表格标签分别显示“可缩短总时长”“可减少等待时间”“可降低等待人数峰值”或“需关注等待情况”。

预警直接复用上方“容量调整建议”的 `surface advice-card` 样式与 `close-button`，统一背景、细边框、圆角、阴影及内边距，不再设置左侧强调色条。中性状态也采用相同配色。

两处提示独立关闭，但使用同一个有效方案签名 `adviceSignature` 判断何时重新出现。预警的关闭签名保存在 `testflow-diagnostics-dismissal-v1`，不修改现有方案和界面偏好数据格式。有效方案变化后清除关闭状态；普通重新渲染、切换视图、缩放、摘要指标选择、仅修改试算输入、导出和刷新均不重置。无效输入不会提前重置；修正后若有效方案仍相同，继续保持关闭。不能使用浏览器存储时保留当前页面内的关闭状态。

关闭后手动点击“查看瓶颈详情”或站点标签，在详情对话框中查看依据，不重新显示已关闭的页面预警。应用试算属于实际方案变化，会重新显示提示；查看试算本身不会改变方案。

新增 `tests/capacity-preferences.py`。默认离线模式使用明确标注的内存存储 fixture；设置 `TESTFLOW_REAL_STORAGE=1` 时使用路由 HTTP 来源、真实 localStorage 和临时持久浏览器配置，并检查浏览器重启后的数据保留。GitHub Actions 的 `Test capacity interface` 运行真实存储模式及原有浏览器用例。
